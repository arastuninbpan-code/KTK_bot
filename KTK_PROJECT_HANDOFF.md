# KTK — полный контекст проекта для переноса в ChatGPT

> Этот файл нужно загрузить в новый проект ChatGPT целиком. Он описывает текущее состояние системы, архитектуру, правила работы и важные ограничения. Исходный код находится в GitHub: https://github.com/arastuninbpan-code/KTK_bot

## 1. Что это за проект

KTK («Кто такая Кристина») — система для театра, в которой руководство ведёт сотрудников, площадки и расписание в Google Таблице, а сотрудники пользуются:

- веб-приложением: https://kstoshasmena.ru/
- Telegram-ботом: `@k_t_k_bot`
- ботом сообщества VK: https://vk.ru/kstoshasmena

Основная Google Таблица:
https://docs.google.com/spreadsheets/d/1VadKiJqbcJn7dsCbQAGfDtSynqe-pX964VRShD18a6U/edit?gid=1621858438#gid=1621858438

GitHub:
https://github.com/arastuninbpan-code/KTK_bot

Система работает без собственного платного сервера:

- Google Sheets — база данных и рабочий интерфейс директора;
- Google Apps Script — API, логика Telegram/VK, уведомления и синхронизация;
- GitHub Pages — веб-приложение;
- Cloudflare Worker — посредник между сайтом/ботами и Apps Script, а также прогрев;
- GitHub Actions — тестирование и автоматическая публикация Apps Script и сайта.

## 3. Вход сотрудников

Телефон для входа больше не используется.

У каждого сотрудника есть:

- шестизначный ID, который выдаёт директор;
- шестизначный PIN сотрудника.

Первичная активация:

1. Директор добавляет сотрудника в лист «Сотрудники» и выдаёт одноразовый ID.
2. Сотрудник вводит ID в Telegram, VK или приложении.
3. Система предлагает придумать постоянный шестизначный PIN.
4. PIN записывается в таблицу, статус меняется на «Активирован».
5. Один комплект `ID + PIN` работает в приложении, Telegram и VK.

В приложении две отдельные графы: ID и PIN. Сообщение бота содержит удобный блок для копирования:

```text
ID: 123456
PIN: 654321
```

Уже подключённый чат нельзя случайно переключить на другого сотрудника отправкой чужих цифр.

## 4. Защита входа

После каждых пяти неверных попыток ступень блокировки повышается:

1. 15 минут;
2. 30 минут;
3. 60 минут;
4. полная бессрочная блокировка.

Защита считается одновременно:

- для конкретного чата или браузера;
- для учётной записи сотрудника целиком.

Поэтому смена браузера, Telegram или VK не должна обходить блокировку.

Во время таймера даже правильный PIN не принимается. Команда `/start`, повторный ID и новое сообщение таймер не сбрасывают.

При полной блокировке в колонке «Статус входа» появляется `Вход заблокирован`.

Разблокировать сотрудника может администратор в уже подключённом боте:

```text
/unlock 123456
```

Здесь `123456` — ID сотрудника. Команда очищает все счётчики и возвращает статус `Активирован`.

Успешный вход очищает незавершённые ступени блокировки.

## 5. Роли и права

Роли:

- `Админ` — полный доступ;
- `Редактор` — редактирование расписания и рабочих сущностей;
- `Читатель` — просмотр своих смен и доступных данных;
- `Заблокирован` или снятая галочка «Доступ» — вход закрыт.

Владелец системы защищён отдельно: его нельзя окончательно удалить, понизить или лишить доступа случайной правкой таблицы.

## 6. Google Таблица

Главные видимые листы:

- `Расписание`;
- `Сотрудники`;
- `Площадки`.

Также могут быть видны `Архив` и `Отчёты`. Остальные листы служебные и обычно скрыты.

### Лист «Сотрудники»

Основные колонки:

- ФИО;
- телефон — историческое/внутреннее поле, для входа не требуется;
- роль;
- ID сотрудника;
- PIN;
- статус входа;
- доступ;
- комментарий;
- группы/должности с галочками.

ID и PIN должны находиться рядом среди закреплённых колонок. Нельзя переименовывать системные заголовки или редактировать сам список вариантов выпадающей ячейки вместо выбора значения.

### Лист «Расписание»

Рабочий формат:

`Дата | Начало | Конец | Событие | Площадка | роли сотрудников…`

Система умеет читать и старый формат, но `styleSheets()` приводит таблицу к текущему виду.

### Лист «Площадки»

Площадки добавляются отдельными строками. В расписании площадку нужно выбирать из выпадающего списка, а не редактировать настройки списка.

### Служебные листы

Ключевые технические листы:

- `_попытки_входа` — ошибки, таймеры, ступени и привязка к сотруднику;
- `_активация` — незавершённая активация в ботах;
- `Подписчики` — привязанные чаты;
- `_служебное` — снимок расписания и напоминания;
- `_недоступность` — даты «не могу работать»;
- `_события`, `_комментарии`, `_фото`, `_аватары`;
- `_лог` — краткая диагностика ботов;
- `_удалённое` и `Архив` — восстановление/история.

Служебные листы нельзя править вручную без понимания кода.

## 7. Возможности приложения

Приложение показывает расписание, смены, площадки, события, собрания и переписку.

Администраторы и редакторы могут править данные согласно ролям. Есть:

- проверка конфликтов площадок;
- недоступность сотрудника по датам;
- комментарии и фотографии;
- аватар из Telegram/VK;
- загрузка аватара из галереи;
- удаление/скрытие аватара;
- отчёты;
- офлайн-очередь безопасных повторных отправок;
- автоматическое обновление после изменения таблицы.

Токен сессии подписан HMAC-SHA256, хранится в браузере и перестаёт работать после изменения ID/PIN. Срок сессии — 30 дней.

## 8. Возможности ботов

Основные команды и кнопки:

- «Мои смены» / `/shifts`;
- «Расписание» / `/schedule`;
- «Приложение» / `/app`;
- «Мой логин» / `/login`;
- «Отключить» / `/stop`;
- публикация афиши `/post` для редакторов;
- разблокировка `/unlock ID` только для администратора.

`/stop` отвязывает конкретный чат и отключает уведомления. Повторный `/start` запускает вход заново.

Уведомления приходят:

- при назначении на смену;
- при снятии со смены;
- при изменении даты, времени, площадки или роли;
- за сутки;
- примерно за час до смены.

Повторы подавляются. Заблокировавший бота пользователь автоматически отвязывается.

## 9. Синхронизация и скорость

Публичная страница обычно загружается примерно за 0,2 секунды, Cloudflare отвечает примерно за 0,3 секунды.

Главное ограничение — Google Apps Script:

- холодный запуск иногда занимает 5–12 секунд;
- незакэшированное чтение листа — около 0,4 секунды;
- после ручной правки таблицы система ждёт несколько секунд тишины, чтобы не отправить промежуточные уведомления по недописанной строке.

Уже реализовано:

- прогрев Apps Script через Cloudflare Cron;
- кэш основных и служебных листов, включая авторизацию и активацию;
- чтение листа один раз за запрос;
- дешёвая проверка версии данных без чтения таблицы;
- быстрый ответ webhook через Cloudflare Worker;
- обход глобальной блокировки для команд, которые только читают расписание;
- группировка нескольких изменений в одно уведомление.

Полностью убрать редкие холодные старты без переноса API с Apps Script на постоянный сервер нельзя.

## 10. Безопасность и важная незакрытая проблема

Проверено:

- токены и приватные ключи не найдены в текущем GitHub и истории;
- секреты должны находиться только в GitHub Secrets, Apps Script Properties и Cloudflare Secrets;
- сайт отдаёт CSP, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer` и запрет камеры/микрофона/геолокации;
- Telegram webhook защищён секретом;
- VK проверяет секрет Callback API;
- API ограничивает размер запроса;
- имя сотрудника не возвращается до проверки PIN;
- роли и токены проверяются сервером, а не только интерфейсом.

### Критично: доступ к Google Таблице

23 ноября 2026 года проверка без авторизации показала, что таблицу можно было скачать целиком как XLSX по ссылке. Если это всё ещё так, у неё включено «Все, у кого есть ссылка».

Поскольку руководство требует хранить PIN в таблице, таблица обязательно должна иметь режим:

`Доступ ограничен`

и конкретные Google-аккаунты руководства. Закрытие публичного доступа не ломает Apps Script: он работает от имени владельца.

Перед дальнейшей работой новый чат должен проверить фактические настройки доступа. Не менять ACL вслепую: сначала получить список аккаунтов руководства, которым нужно оставить доступ.

## 12. Разработка и проверка

Рабочая директория репозитория обычно: `/workspace/KTK_bot`.

Команды:

```bash
cd app
node --test test/*.test.mjs
node build-gas.mjs
```

Перед коммитом обязательно:

1. прогнать все тесты;
2. выполнить `node build-gas.mjs`;
3. проверить `git diff --check`;
4. убедиться, что `apps_script_bot/Code.gs` соответствует исходникам;
5. после push дождаться успешных GitHub Actions;
6. проверить `https://kstoshasmena.ru/version.js`.

Собранный `Code.gs` нельзя править вручную: изменения вносятся в `app/lib/` или `app/gas/`, затем запускается сборка.

## 13. Публикация

После push в `main`:

- GitHub Actions тестирует и публикует Apps Script;
- GitHub Pages публикует `docs/`;
- версия сайта задаётся в `docs/version.js`;
- версия API задаётся в `app/lib/api.mjs` (`SERVER_VERSION`);
- при обновлении сайта меняется имя кэша в `docs/sw.js` и версии ресурсов в `docs/index.html`.

Cloudflare Worker может требовать отдельной публикации через Cloudflare, если у аккаунта не настроен автоматический деплой из GitHub.

## 14. Секреты — не вставлять в чат и GitHub

Необходимые значения существуют во внешних настройках, но не должны попадать в исходники:

- `SHEET_ID`;
- `TELEGRAM_BOT_TOKEN`;
- `VK_TOKEN`, `VK_GROUP_ID`, `VK_SECRET`, `VK_CONFIRM`;
- `WEBHOOK_SECRET`;
- `SESSION_SECRET`;
- `APP_URL`, `RELAY_URL`;
- `OWNER_PHONE`, `OWNER_NAME`, `OWNER_LOGIN`;
- Cloudflare `GAS_URL`, `PATH_SECRET`;
- GitHub secret `CLASPRC_JSON`.

Если секрет когда-либо случайно появился в сообщении, логе или репозитории, его нужно не просто удалить, а перевыпустить.

## 15. Правила для нового ChatGPT

При дальнейшей работе:

1. Сначала изучить репозиторий и актуальное состояние `main`, не полагаться только на этот файл.
2. Не ломать существующую таблицу и не менять названия системных колонок без миграции.
3. Не редактировать вручную собранный `apps_script_bot/Code.gs`.
4. Любую логику входа проверять одновременно в приложении, Telegram и VK.
5. Проверять сценарии: неверный ID, неверный PIN, правильный PIN во время блокировки, смена браузера/канала, истечение таймера, полная блокировка и разблокировка директором.
6. Не публиковать PIN, телефоны, chat ID, токены и содержимое служебных листов.
7. Не менять права Google Таблицы без списка аккаунтов, которым необходимо оставить доступ.
8. Перед деплоем прогонять весь набор тестов.
9. После деплоя проверять живую версию сайта и статус GitHub Actions.
10. Общаться с владельцем проекта по-русски, просто и без лишнего технического жаргона; он ожидает, что изменения будут реализованы и опубликованы полностью.
